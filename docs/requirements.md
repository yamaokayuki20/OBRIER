## 1. サービス概要

### 1.1 サービスの内容

オブリエは、SlackやTeamsなど社内コミュニケーションツールのやり取りから感謝の言葉を自動で検出し、受け取った本人の「ありがとうアルバム」に綴じるサービスである。本人は届いた感謝を一覧で見返すことができ、感謝の傾向から自分の役割や得意（カタチ）を知ることができる。上司はメンバーのアルバムと月次レポートを閲覧し、1on1や評価、アサインの参考にできる。

### 1.2 名称の由来

オブリエ（OBRIER）は、obrigado（ポルトガル語：ありがとう）と relier（フランス語：綴じる・結ぶ）を組み合わせた造語である。両語はラテン語 ligare（結ぶ）を共通の語源に持ち、「感謝」と「絆」が同じ根から生まれた言葉であることをブランドの物語とする。

### 1.3 背景・解決したい課題

リモートワークの浸透により、社内における自分の役割や貢献を実感しにくくなっている。感謝の言葉はチャット上で日々生まれているにもかかわらず、流れて消えてしまい、本人の自己肯定感や上司のマネジメントに活かされていない。
- 本人：自分の貢献が見えず、自己肯定感が持てない。強みを確信できずキャリアに踏み出せない
- 上司：リモートでメンバーの貢献や不調が見えない。1on1・評価の材料が不足している
- 組織：感謝を伝える文化が根付かず、チームの空気が硬い

### 1.4 サービスの狙い

- 狙い① 達成感・自己肯定感を感じることができ、自信につながる
- 狙い② よく感謝されることから、自分の役割や得意が見えるようになる
- 狙い③ 自然と相手に感謝を伝えたくなり、チームの空気感が良くなる

### 1.5 ターゲット

| 対象 | 像 | 主な利用目的 |
|---|---|---|
| 本人（主対象） | 自分の役割・貢献を自覚できず自己肯定感が低い社員（例：文系出身SE3年目・26歳） | アルバムの見返し／得意の発見 |
| 上司 | リモート下でメンバーの貢献が見えにくい管理職 | メンバー把握／1on1・評価・アサイン |
| 導入企業 | ビジネスチャットを利用する企業 | エンゲージメント向上 |

### 1.6 提供形態

企業導入（B2B）を前提とするWebアプリケーション。個人課金プランも将来的に用意する（二段構え）。無料枠の機能制限は設けない。

## 2. 基本方針

- アルバム型デザイン：宝物を綴じるアルバムの世界観をUI全体で表現する。カードは白い紙の1枚とし、上端に場面タグ色の帯を置く。これを方眼（グラフ用紙）の台紙に貼る。カードの丈は全枚そろえる
- 会社導入前提：企業（上司・管理者）は個々人のありがとうアルバムを閲覧できる
- 非ランキング：個人間の順位付け・ランキング表示は行わない
- 静かで温かいトーン：通知・文言・演出から比較や急かしの表現を排除する
- キザな言い回しを避ける：UIの操作フィードバックには「綴じました」等の比喩を用いず「保存しました」と平易に書く。「綴じる」はサービス名の由来・コンセプト説明にのみ用いる
- 通知は控えめ：本人向け通知は週1回のメールダイジェストのみ

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| 感謝カード | 検出された感謝の言葉1件。送り主・経緯・場面タグを持つ。表示は白い紙の1枚とし、上端に場面タグ色の帯を置いて表現する |
| アルバム | 本人が受け取った感謝カードの一覧画面。月ごとに綴じられる |
| 拡大詳細 | 感謝カードを押したときに開く詳細ビュー。送り主・チャネル・日時、オブリエのメモ、やり取りの流れ、元のメッセージを開く導線、お気に入り、じぶんのメモ（本人のみ）、削除を含む。カードの裏面（めくり）は設けない |
| カタチ | 本人の得意を表す一連の可視化の総称。場面タグの件数内訳、よく感謝される場面（TOP10まで）、受信・送信の推移チャート、広がりマップで構成する。レーダーチャートは用いない |
| 場面タグ | 感謝の場面を表すタグ。固定分類ではなく、感謝の内容からLLMが自動生成し増える。代表的な7種（スピード対応／資料品質／調整力／気配り／後輩サポート／アイデア／情報共有）には固有色を割り当て、感謝カード上端の帯・タグピル・日付スタンプの色として用いる |
| 経緯 | 感謝が生まれた元のやり取り（前後の会話）。拡大詳細では「やり取りの流れ」として表示する |
| オブリエのメモ | AIが経緯や傾向を言語化した短い解説文 |
| じぶんのメモ | 本人だけが読み書きできる自由記述メモ。上司・管理者には一切表示しない |
| 開封の儀 | 月に一度まとめて開封する演出付き振り返り体験。**v1.1で廃止**し、以後実装しない（用語としても使用しない） |
| 月次レポート | 上司向けの1枚もの。メンバーの感謝の定量サマリー・代表エピソード・アラートを含む。上司向けには「1on1準備メモ」と呼ぶ |
| カタチレポート | 本人向けの月次レポート。カタチの変化と代表エピソードをAIが文章で言語化したもの |

## 4. 機能要件

### 4.1 取り込み・検出

| ID | 機能名 | 概要 | 優先度 |
|---|---|---|---|
| F01 | 感謝の自動検出 | 明示的表現（ありがとう等）と暗黙的表現（助かった・さすが・おかげで等）をLLMで検出し宛先本人のアルバムに綴じる | 高 |
| F02 | 誤検出の除外と学習 | 拡大詳細から「これは感謝ではない」と報告できる。報告したカードはアルバムから外れ、報告内容を検出器の学習（判定プロンプトの負例・閾値調整）に反映する。**【判断待ち】** 拡大詳細の報告導線はイシュー#24でユーザー判断により削除済み（プロトタイプには存在しない）。ただし対応表No.2で「対応する」と決めた機能であるため独断では取り下げず、機能自体を取り下げるか(a)、報告導線を別の場所へ移すか(b)は未確定（decision-log D-75。管理者の検出品質モニタ＝F24には報告件数の表示だけが残っており、この判断が付くまで暫定表示） | 高 |
| F03 | 皮肉・定型文フィルタ | 皮肉表現・自動送信定型文を検出対象から除外する | 中 |
| F04 | 絵文字リアクション取り込み | 感謝系絵文字（🙏✨👏等）を「小さなありがとう」として計上する。カードは作らず、カタチ画面に件数を控えめに表示するのみとする（アルバムには出さない） | 中 |
| F05 | 過去ログ遡り取り込み | 初回連携時に過去1年分を解析し、初回起動時からアルバムが埋まった状態にする | 高 |

## 5. 対象外事項（今回開発しない）

- 対面・電話等チャット外の感謝の手動記録／Slack・Teams以外の連携（Chatwork等）
- 「意外な得意」の指摘／落ち込み日の特別表示／開封の儀（月次演出。v1.1で廃止）
- 感謝の返礼導線／感謝の気づきサジェスト／チーム全体量の表示
- データポータビリティ（退職時持ち出し）／解析範囲のオプトイン設定（会社導入の規約側で対応）
- 人事・経営向け分析機能（後日検討）／メンバー間の得意マップ／多言語対応／AI対話履歴の取り込み

## 7. 非機能要件

| 分類 | 要件 |
|---|---|
| 検出品質 | 誤検出率・見逃し率を継続測定し、フィードバック（F02）で改善する。信頼度が低い候補は表示しない |
| プライバシー | 感謝と判定されたメッセージのみ保存し、それ以外は解析後速やかに破棄する。閲覧権限は本人・直属上司・管理者に限定し、上司の閲覧操作は監査ログに記録する |
| 性能 | アルバム一覧の初期表示1.5秒以内。検出からカード反映まで5分以内 |
| 可用性 | 稼働率99.5％以上（業務時間帯） |
| トーン&マナー | 順位・比較・催促を想起させる表現の禁止。通知文言は言葉調とする。UIの操作フィードバックはキザな言い回しを避け平易に書く（例：「綴じました」ではなく「保存しました」） |
| デザイン | 白地×薄い青の方眼を台紙とし、感謝カードは白い紙＋上端の場面タグ色の帯で表現する。感謝本文はゴシック体。カードはまっすぐ置き、丈は全枚そろえて中身の量は行数で受け止める。奥行き（3D）を持たせるのはアバターのみとする |
| セキュリティ | 通信TLS、保存データ暗号化。連携トークンは秘匿管理 |
| 対応環境 | PCおよびスマートフォンのブラウザ（レスポンシブ対応必須） |

## 8. 前提・制約

- Slack（Events API）・Microsoft Teams（Graph API）が利用可能であること
- 感謝判定・分類・要約にLLMを利用する。API利用コストは運用設計で管理する
- 導入企業は利用規約・社内周知（メッセージ解析が行われること）を整備すること
