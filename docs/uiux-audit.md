## 0. 総評

**「見せたいもの」は美しく作れているが、「使えるか」の検証がまだ一度も行われていない段階にある。**

紙とタグ色でアルバムの世界観を成立させた造形、量に応じた3種のカード、めくりを1要素の裏返しで実装した遷移、じぶんのメモを上司ビューから完全に落としている権限設計は、確定した設計原則を正確に守れており、B2B SaaS の平均を上回る。

一方で、**キーボードだけでは本人の3タブを切り替えることすらできず**（`div` にタブロールも `tabindex` も無い）、**拡大詳細を開くとフォーカスが body に落ちて背景のカード群へ流れていく**。二次テキストに使っている色トークン `--stage-ink-soft` は白地で **3.92:1**（WCAG AA は 4.5:1）で、画面の見出し・説明文・月ディバイダー・タブ・チェックボックスのラベルまで、実測 **215箇所**が基準を割っている。日本の大企業向けB2B SaaS は調達要件で JIS X 8341-3（＝WCAG 2.1 AA 相当）の適合表明を求められることが多く、この状態のまま実装に進むと、後から全画面の色設計をやり直すことになる。

加えて、**画面に出ている数字が画面ごとに違う**（アルバム「264通」／カタチ「265通」／実際のカード12枚／CSVダイアログ「12件」／上司一覧の高橋さん「2通」／同じ人の1on1メモ「6通」）。プロトタイプ由来のズレではあるが、このサービスの価値は「自分に届いた感謝の量と内容を信じられること」に全面的に依存しており、**数字が合わないことは世界観の破壊と同義**である。ここは実装前に必ず一本化してほしい。

指摘は全48件（Blocker 3／Critical 9／Major 21／Minor 15）。すべて `CLAUDE.md` の設計原則および `decision-log.md` の「対応しない」判断と矛盾しないことを1件ずつ確認済みで、**世界観を薄める方向の提案は1件も含めていない**。

## 1. 監査基準

各基準は合否判定できる形で書く。**MUST** は満たさないまま実装に進んではいけないもの、**SHOULD** は一流B2B SaaSと並ぶために必要なもの。

### 1.1 情報設計・ナビゲーション（IA）

| ID | 区分 | 基準 |
|---|---|---|
| IA-1 | MUST | 現在いる画面が、選択中タブの視覚的強調と `aria-current`／`aria-selected` の**両方**で示されていること |
| IA-2 | MUST | 階層を1段下りる画面（メンバー詳細・拡大詳細）から、元の一覧へ戻る導線が常に画面内に存在すること |
| IA-3 | MUST | 画面の主役コンテンツが、1280×900 および 390×844 の**ファーストビュー内に出現を開始**していること（主役の上端がビューポート高の70%以内） |
| IA-4 | SHOULD | ビュー切替時に `document.title` が更新され、支援技術の利用者にも現在地が伝わること |
| IA-5 | SHOULD | 同一の状態（絞り込み等）が2つ以上のUIに重複表示されていないこと |

### 1.2 視覚設計

| ID | 区分 | 基準 |
|---|---|---|
| VD-1 | MUST | 見出し・本文・補足の3階層が**文字サイズで**区別されていること（見出しは本文の1.25倍以上） |
| VD-2 | MUST | 見出しに見える要素が、見出し要素（`h1`〜`h4`）として実装されていること |
| VD-3 | MUST | 余白が定義済みのスケール（4/8/12/16/20/24px 等）から選ばれ、`style` 属性での場当たりな上書きが同種要素間で発生していないこと |
| VD-4 | SHOULD | 色が意味を担う場合、色以外の手がかり（文言・アイコン・位置）が併記されていること |
| VD-5 | SHOULD | 文字サイズが相対単位で定義され、ブラウザの既定文字サイズ設定を尊重すること |

### 1.3 インタラクション

| ID | 区分 | 基準 |
|---|---|---|
| IX-1 | MUST | すべての操作に、**押した瞬間**（押下フィードバック）と**終わった後**（結果）の2段階の反応があること |
| IX-2 | MUST | 破壊的操作（削除・報告）は、確認ダイアログに**対象の中身を再掲**したうえで実行されること |
| IX-3 | MUST | 未保存の入力を持つ面を閉じるとき、破棄されることが利用者に伝わること |
| IX-4 | MUST | 楽観的更新を行った場合、**同じデータを表示している他の場所**（一覧・件数・絞り込み結果）も同時に更新されること |
| IX-5 | SHOULD | 完了通知は消えるまでに最低4秒あり、支援技術にも通知されること |
| IX-6 | SHOULD | 200ms を超える処理には進行中の表示があること |

### 1.4 状態の網羅

| ID | 区分 | 基準 |
|---|---|---|
| ST-1 | MUST | 各一覧に **0件／1件／通常／大量（100件以上）** の4状態が定義され、実際に表示できること |
| ST-2 | MUST | 0件状態に、**その状態を脱するための操作**（絞り込み解除など）が含まれること |
| ST-3 | MUST | 外部連携を持つ画面に **接続中／未接続／トークン失効／取り込み中／失敗** の状態が定義されていること |
| ST-4 | MUST | 通信失敗時の表示（何が起きたか・利用者は何をすればよいか）が定義されていること |
| ST-5 | SHOULD | 読み込み中はスケルトンまたはプレースホルダで、確定後のレイアウトと同じ形が示されること |
| ST-6 | SHOULD | 権限がない領域は、非表示ではなく「権限がないため表示できない」と示すか、そもそも導線を出さないかが一貫していること |

### 1.5 フォームと入力

| ID | 区分 | 基準 |
|---|---|---|
| FM-1 | MUST | すべての入力欄に、`label` 要素または `aria-label` による**永続的な**名前があること（プレースホルダのみは不可） |
| FM-2 | MUST | スマートフォンで入力欄の文字サイズが16px以上であること（iOS Safari の自動拡大回避） |
| FM-3 | MUST | 設定変更（権限・所属など影響範囲の大きいもの）は、確認または取り消し手段を伴うこと |
| FM-4 | SHOULD | 自由記述には保存状態（未保存／保存済み）が表示されること |
| FM-5 | SHOULD | 必須・任意の別が、入力前に分かること |

### 1.6 アクセシビリティ

| ID | 区分 | 基準 |
|---|---|---|
| AC-1 | MUST | 本文テキストのコントラスト比 **4.5:1 以上**、18.66px以上かつ太字または24px以上は **3:1 以上**（WCAG 2.1 SC 1.4.3 AA） |
| AC-2 | MUST | UI部品の境界・状態表示・フォーカスリングのコントラスト比 **3:1 以上**（SC 1.4.11） |
| AC-3 | MUST | すべての操作がキーボードだけで完結し、Tab順が視覚順と一致すること（SC 2.1.1／2.4.3） |
| AC-4 | MUST | フォーカスされた要素にフォーカスリングが**必ず見える**こと（SC 2.4.7） |
| AC-5 | MUST | モーダルは、開いたら中へフォーカスを移し、内部で循環し、Escで閉じ、**元の起動要素にフォーカスを戻す**こと。背景は `inert` 等で不活性にすること |
| AC-6 | MUST | 操作の結果（保存・削除・エラー）が `aria-live` で通知されること（SC 4.1.3） |
| AC-7 | MUST | タップ標的が **24×24 CSS px 以上**（WCAG 2.2 SC 2.5.8 AA） |
| AC-8 | SHOULD | タッチ操作面のタップ標的が **44×44 CSS px 以上**（Apple HIG／Material） |
| AC-9 | MUST | ホバーでしか得られない情報が存在しないこと。同じ情報がタップ・フォーカス・読み上げでも得られること（SC 1.3.1／1.4.13） |
| AC-10 | MUST | 横スクロール領域がキーボードで操作可能であること（`tabindex="0"` 等） |
| AC-11 | MUST | `prefers-reduced-motion: reduce` で、位置・拡大の伴うアニメーションが行われないこと |
| AC-12 | MUST | 320px 幅で横スクロールが発生しないこと（SC 1.4.10） |
| AC-13 | SHOULD | テキスト間隔の変更（行送り1.5・字間0.12em・語間0.16em、SC 1.4.12）で文字が欠落しないこと |
| AC-14 | SHOULD | ソート可能な列に `aria-sort`、タブに `role="tab"`／`aria-selected` が付与されていること |

### 1.7 レスポンシブ

| ID | 区分 | 基準 |
|---|---|---|
| RS-1 | MUST | 375／390／768／1280／1920 のいずれでも、ページ本体に横スクロールが発生しないこと |
| RS-2 | MUST | 意図的な横スクロール領域（幅広テーブル・長期チャート）に、スクロール可能であることの視覚的な示唆があること |
| RS-3 | MUST | 固定・粘着要素がコンテンツと重なって文字を読めなくしないこと |
| RS-4 | SHOULD | 390px でヘッダーの占有高が 88px 以下であること |

### 1.8 マイクロコピー

| ID | 区分 | 基準 |
|---|---|---|
| MC-1 | MUST | 敬体（です・ます）で統一されていること |
| MC-2 | MUST | 比較・順位・催促・叱責を想起させる表現が無いこと |
| MC-3 | MUST | 操作フィードバックにキザな比喩を用いないこと（「綴じました」ではなく「保存しました」） |
| MC-4 | MUST | 同じ結果をもたらす操作の完了文言が、同じ語彙・同じ粒度で書かれていること |
| MC-5 | SHOULD | 完了文言が「何が」「どうなったか」を含むこと（対象名を含む） |

### 1.9 パフォーマンス体感

| ID | 区分 | 基準 |
|---|---|---|
| PF-1 | MUST | 一覧の初期表示が **1.5秒以内**に完了すること（要件定義 非機能） |
| PF-2 | MUST | 演出の所要時間が件数に比例して伸びないこと（件数によらず上限が決まっていること） |
| PF-3 | SHOULD | 一覧が30件単位でページングされること（基本設計 8章） |

### 1.10 信頼感・安心感

| ID | 区分 | 基準 |
|---|---|---|
| TR-1 | MUST | 同一の事実を表す数値が、全画面で一致すること |
| TR-2 | MUST | 誰に見えるか／見えないかが、該当する面の中で明示されていること |
| TR-3 | MUST | 復元不可の操作は、対象を再掲した確認を経ること |
| TR-4 | MUST | 上司・管理者の閲覧が監査ログに記録され、記録範囲が明示されていること |
| TR-5 | SHOULD | AIが生成した文（オブリエのメモ・カタチレポート）が、AI由来であると分かること |

## 3. 指摘一覧（重大度順サマリ）

重大度の定義：
- **Blocker** … この状態で実装に着手すると、後戻りコストが全画面規模になる。または特定の利用者が機能を一切使えない。
- **Critical** … 主要な利用者行動が完遂できない、または要件定義・設計書に明記された仕様に反する。
- **Major** … 一流B2B SaaSと比べて明確に見劣りする、信頼を損なう。
- **Minor** … 品質の底上げ。実装フェーズで拾えばよい。

| ID | 重大度 | 観点 | 一行要約 | 難易度 |
|---|---|---|---|---|
| A-01 | Blocker | アクセシビリティ | 本人の3タブが `div` でキーボードから操作できない | 低 |

## 4. 指摘の詳細

### A-01｜Blocker｜アクセシビリティ／情報設計
**本人の3タブが `div` でキーボードから操作できない**

- **現状**（実測）：`#personTabs` の3つのタブは `<div class="tab" data-v="...">`（L597-601）。`tabindex` なし・`role` なし。Tabキーで45回巡回した実測結果では、ロール切替（本人／上司／管理者）→ rev表示 → 節目の✕×3 → 場面select → … と進み、**3タブは一度も現れない**。キーボードだけの利用者は「あなたのカタチ」「おくった ありがとう」に到達できない。
- **あるべき姿**：`<button>`（または `role="tab"` ＋ `tabindex` 管理）にし、`aria-selected="true"`／`aria-current="page"` を付与する。Tab順は「ブランド → 主タブ3つ → ロール → 本文」とし、視覚順と一致させる。左右矢印キーでのタブ移動（APG Tabs パターン）を実装すればなお良い。
- **該当箇所**：L597-601（HTML）、L104-106（`.tab` CSS）、L2454-2455（イベント登録）
- **難易度**：低（`div`→`button` 置換とCSSの `border:none; background:none` 追加のみ）
- **原則抵触**：なし。見た目は完全に維持できる。

### A-02｜Blocker｜アクセシビリティ
**モーダルにフォーカス制御が一切ない**

- **現状**（実測）：カードをEnterで開いた直後、`document.activeElement` は **body**。そこからTabを12回押すと、フォーカスは**背景のカード群**を順に巡り、ダイアログ内には一度も入らない（`insideDialog: false` が12回連続）。背景の `main` に `inert` も `aria-hidden` もない。Escで閉じた後のフォーカスは起動元のカードに戻らない。
- **あるべき姿**：(1) 開いたら最初のフォーカス可能要素（または `.sheet-head` の見出し）へ移動、(2) Tab／Shift+Tab をダイアログ内で循環、(3) 背景に `inert` を付与、(4) 閉じたら**起動元のカードへフォーカスを戻す**。`role="dialog" aria-modal="true"` は既にあるので、残りは実装のみ。`aria-label` ではなく `aria-labelledby` で見出しを参照する形が望ましい。
- **該当箇所**：L1594-1728（`openThread`）、L1553-1578（`openDialog`）
- **難易度**：中（共通のフォーカストラップ関数を1つ作り、2箇所から呼ぶ）
- **原則抵触**：なし。原則4の「1つの要素ごと裏返す」遷移はそのまま維持できる（裏面 `.f-back` にフォーカスを移すだけ）。

### A-04｜Critical｜アクセシビリティ／インタラクション
**推移チャートの数値がホバー限定**

- **現状**（実測）：数値の表示は `inner.addEventListener("mousemove", ...)`（L1951）のみ。`touchstart`／`focus`／キーボードの経路がない。SVGは `role="img" aria-label="もらった・おくったの推移"` のみで、値を読む手段がない。Y軸の目盛ラベルは0本（X軸ラベルのみ12本）。スマートフォンでは説明文が「チャートに**マウス**をのせると、その時点の数が見られます」と表示される（L2032）。**390pxの利用者は推移の数値を一切読めない**。
- **あるべき姿**：(1) タップ／ドラッグでもクロスヘアと数値を表示、(2) チャートに `tabindex="0"` を与え左右矢印で系列を辿れるようにし、選択点を `aria-live="polite"` で読み上げる、(3) 視覚的に隠した `<table>`（またはアコーディオンで開ける表）を代替として置く、(4) Y軸に最大値・中央値の2目盛だけ付ける、(5) 説明文を「チャートをなぞると、その時点の数が見られます」に変更。
- **該当箇所**：L1899-1975（`chartWidget`）、L2032（説明文）
- **難易度**：中
- **原則抵触**：なし。「通常時は数値ラベルなし」（実装上の重要仕様）は維持される。**Y軸目盛の追加だけは「数値ラベルなし」の解釈に触れうるため、要判断**（本監査は「点ごとの数値ラベル」を指すと解釈した）。

### A-05｜Critical｜アクセシビリティ
**メンバー一覧のソートがマウス専用**

- **該当箇所**：L674-679、L385-386（CSS）、L2185-2186、L2467-2468
- **難易度**：低
- **原則抵触**：なし（原則6は「上司テーブルのソートは許可されている」と明記）。

### A-06｜Critical｜信頼感／状態の網羅
**「264通」に対しカードは12枚、ページングも「もっと見る」もない**

- **現状**（実測）：ヘッダーの累計は `264`（L620、ハードコード）、実際に描画されるカードは **12枚**。12枚目の下は何もなく、「これで全部なのか」「読み込みが失敗したのか」が分からない。基本設計8章は「カードはページング（30件単位）で取得する」と定めているが、UIにその概念がない。

- **難易度**：中
- **原則抵触**：なし。

### A-07｜Critical｜信頼感／マイクロコピー

## 5. 評価できる点（維持すべきもの）

一流B2B SaaSと比べても優れている、または確定した設計原則を正確に守れている点。**改修時にこれらを壊さないこと。**

1. **プライバシーの明示が全画面で徹底されている**（TR-2 合格）。上司ビューのカード詳細を実測したところ、`memo-ta` なし・`data-del` なし・`data-not-thanks` なし・`data-fav` なしで、代わりに「じぶんのメモは本人だけのものです。上司・管理者には表示されません。」が表示される。上司パネルには「このパネルは本人には表示されません」、管理者画面にも「じぶんのメモは、管理者からも参照できません」。原則8を実装レベルで守れている。
2. **`prefers-reduced-motion` の対応が正しい**（AC-11 合格）。実測で遷移アニメーション0件、詳細を即時表示、波紋・トーストのアニメも抑止。ここまで丁寧に対応しているプロトタイプは稀。
3. **日本語の文字サイズ基準が明文化され、実装されている**。デジタル庁基準・JLReq・iOS Safari の16px問題まで踏まえたコメント（L38-75、L166-173）は、実装者への引き継ぎとして極めて質が高い。
4. **カードの3種類（短い一言／中くらい／長文）が破綻しない**。1280・390の両方で、`kind-long` のみが省略され「…続きは詳細で」が出る。53文字の境界値でも破綻しないことを実測で確認済み。丈は全枚320pxで揃っている。
5. **マイクロコピーが原則どおり**。UI文言に「綴じ」は0件、比較・順位・催促の表現もない。「順位はつけていません。」と能動的に宣言している点も良い。
6. **320px でのリフロー**（AC-12 合格）。
7. **性能に対する設計の記録**。D-24〜D-26 の経緯がコード内コメントとして残っており、なぜその実装なのかが読める。この文化は実装フェーズでも維持すべき。

### 7.2 コントラスト計算の方法と注意

- `getComputedStyle` から `color` と、祖先を遡って合成した実効背景色を取得し、`opacity` の累積を文字色のアルファに掛けたうえで WCAG 2.x の相対輝度式で算出した。
- **背景が `background-image`（グラデーション）の要素は、白背景として計算される**。該当はブランドマーク「O」のみで、実際は白文字 on `#d89a48→#b9752c` ＝ 2.45〜3.74:1。ただし **WCAG 1.4.3 はロゴタイプを対象外**としているため、指摘には含めていない。
- 大きい文字の判定は「24px以上、または18.66px以上かつ700以上」とした。
