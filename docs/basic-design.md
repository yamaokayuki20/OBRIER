## 1. システム構成

オブリエは、チャット連携層・検出分類エンジン・アプリケーション層の3層で構成するWebアプリケーションである。

| 構成要素 | 役割 | 主な技術（想定） |
|---|---|---|
| チャット連携層 | Slack/Teamsからのメッセージ受信（リアルタイム）と過去ログ取得（バッチ） | Slack Events API／MS Graph API |
| 検出分類エンジン | 感謝判定・宛先解決・場面分類・皮肉除外・経緯抽出・要約生成 | LLM API＋ルールベース前段 |
| アプリケーションサーバ | 画面向けAPI提供・権限制御・レポート生成・通知 | Web API サーバ |
| データストア | 感謝カード・経緯・レポート等の永続化 | RDB（PostgreSQL想定） |
| バッチ基盤 | 過去ログ取込・月次レポート生成・週次メール・アラート判定 | ジョブスケジューラ |
| フロントエンド | 本人ビュー・上司ビューのSPA | Web（レスポンシブ） |

### 1.1 データフロー概要

① チャットでメッセージ発生 → ② 連携層が受信し一次フィルタ → ③ 検出分類エンジンが感謝判定・分類・経緯抽出 → ④ 感謝カードとして保存 → ⑤ 本人のアルバム／上司のダッシュボードに反映 → ⑥ 週次・月次バッチがダイジェストとレポートを生成する。感謝と判定されなかったメッセージは保存しない。

## 2. 画面設計

### 2.1 画面遷移

本人：アルバム（S01）⇔ カタチ（S02）⇔ おくった（S03）をタブで切替。カード押下で経緯モーダル（S05）。カタチの場面カードからアルバムのタグ絞り込みに遷移できる。
上司：メンバー一覧（S06）→ メンバー詳細（S07）→ 月次レポート（S08）。詳細からカード押下で経緯モーダル（S05）。
ロールは認証情報に基づき自動で決まる（本人ビューは全員、上司ビューは管理職のみ）。

| 画面 | 目的 | 主要要素 | 主要遷移 |

## 4. 外部連携設計

### 4.1 Slack

- Events API（message.channels 等）でパブリックチャンネルのメッセージを受信する
- 過去ログは conversations.history で初回取込バッチが最大1年分を取得する
- 取得スコープは導入企業の管理者が承認する

### 4.2 Microsoft Teams

- Graph API のチャネルメッセージ購読（change notifications）で受信する
- 過去ログは同APIの一覧取得で取り込む

## 5. 検出・分類設計（概要）

検出はルールベース前段とLLM判定の二段構成とする。前段で候補を絞ることでLLMコストを抑制する。
- 前段：bot・自動定型文の除外、感謝語彙辞書・感謝系絵文字による候補抽出
- LLM判定：対象発言と前後文脈を入力し、感謝該当性／宛先／場面分類／皮肉判定／信頼度を得る
- 閾値制御：信頼度が基準以上のもののみカード化する。基準未満は保存しない
- 経緯抽出：感謝発言から同一スレッド・直前のやり取りを遡り、経緯と要約（オブリエのメモ）を生成する
- 学習：誤検出報告を判定プロンプトの追加事例および閾値調整に反映する

## 6. 通知設計

- 本人向け：週1回のメールダイジェストのみ。文言は「今週は、あたたかい言葉が3通とどいています」のような言葉調とする
- 上司向け：プッシュ通知は行わない。月次レポート生成時にアプリ内で知らせる
- 禁止事項：順位・比較・催促（送りましょう等）を含む通知

| 操作 | 本人 | 上司（直属） | 管理者 |
|---|---|---|---|
| 自分のアルバム閲覧 | ○ | ― | ― |
| メンバーのアルバム閲覧 | × | ○（自チームのみ） | ○ |
| 月次レポート閲覧 | × | ○（自チームのみ） | ○ |
| カードの削除・お気に入り・じぶんのメモ | ○（自分宛てカード） | × | × |
| エクスポート（CSV/STAR） | ○（自分の分） | ○（レポートPDF） | ○ |
| 連携設定・チーム管理 | × | × | ○ |

上司・管理者によるアルバム閲覧は監査ログに記録する。

## 8. 非機能設計（概要）

- 性能：一覧系APIは応答1秒以内を目標とし、カードはページング（30件単位）で取得する
- データ最小化：感謝と判定されなかったメッセージ本文は永続化しない
- 監査：閲覧・エクスポート・設定変更の操作ログを1年間保持する
