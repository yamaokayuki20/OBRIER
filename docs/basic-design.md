## 1. システム構成

オブリエは、チャット連携層・検出分類エンジン・アプリケーション層の3層で構成するWebアプリケーションである。

| 構成要素 | 役割 | 主な技術（想定） |
|---|---|---|
| チャット連携層 | Slack/Teamsからのメッセージ受信（リアルタイム）と過去ログ取得（バッチ） | Slack Events API／MS Graph API |
| 検出分類エンジン | 感謝判定・宛先解決・場面分類・皮肉除外・経緯抽出・要約生成 | LLM API＋ルールベース前段 |
| アプリケーションサーバ | 画面向けAPI提供・権限制御・レポート生成・通知 | Web API サーバ |
| データストア | 感謝カード・経緯・レポート等の永続化 | RDB（PostgreSQL想定） |
| バッチ基盤 | 過去ログ取込・月次レポート生成・週次メール・アラート判定 | ジョブスケジューラ |
| フロントエンド | 本人ビュー・上司ビューのSPA | Web（レスポンシブ） |

### 1.1 データフロー概要

① チャットでメッセージ発生 → ② 連携層が受信し一次フィルタ → ③ 検出分類エンジンが感謝判定・分類・経緯抽出 → ④ 感謝カードとして保存 → ⑤ 本人のアルバム／上司のダッシュボードに反映 → ⑥ 週次・月次バッチがダイジェストとレポートを生成する。感謝と判定されなかったメッセージは保存しない。

## 2. 画面設計

### 2.1 画面遷移

本人：アルバム（S01）⇔ カタチ（S02）⇔ おくった（S03）をタブで切替。カード押下で拡大詳細（S05）。カタチの場面カードからアルバムのタグ絞り込みに遷移できる。
上司：チーム全体サマリ（S06）→（メンバー一覧表の行押下で）メンバー詳細（S07）→（1on1準備メモの履歴から）1on1準備メモ（S08）。**上司ビューにはカード一覧・拡大詳細（S05）への導線を持たない**——イシュー#27でメンバー詳細のアルバム・おくったタブを廃止したため、上司が個々のカードを開く経路は無い（decision-log D-85）。S07の「あなたのカタチ」に相当する部分は本人のS02と同一構成で表示するが、お気に入り・じぶんのメモ・削除といったカード単位の操作は伴わない。
管理者：管理者設定（S09）。ヘッダーの管理者メニューから開く。S09は本人ビュー・上司ビューとは独立した画面で、他画面への遷移は持たない。
ロールは認証情報に基づき自動で決まる（本人ビューは全員、上司ビューは管理職のみ、S09は管理者のみ）。

### 2.3 デザイン方針

アルバムの世界観を、装飾ではなく「白い紙とタグ色の帯」「押しムラのある印」で成立させる。

| 要素 | 方針 |
|---|---|
| 背景（台紙） | 白地×薄い青の方眼（グラフ用紙）。方眼ノートにカードを貼った佇まいとする |
| 感謝カード | **白い紙のカード（#fffdfa・角丸12px）の上端に、場面タグ色の帯（border-top 7px）を置く**。ベタ塗り・マスキングテープは用いない。色は面ではなく帯で示し、紙の白さと余白で言葉を読ませる |
| カードの丈 | **全枚そろえる（固定320px）**。中身の量で丈がばらつかないようにし、量の違いは行数で受け止める（詳細設計 1.1.1） |
| カードの構成 | 上から アバター（中央）／本文／送り主名／最下部にタグピルと日時の行、の順に積む |
| 本文 | 感謝本文はゴシック体（太さ600・字間.06em・行間2.05・16px・中央揃え）。明朝は用いない |
| カードの傾き・質感 | カードはまっすぐ置く。静的な傾き・紙のグレイン・ベタ塗りの紙目はいずれも用いない |
| タグピル・日付 | カード下部の同じ行に並べる。タグピルは淡色地＋濃色文字（いずれもタグ色からの派生色）とする |
| 日付 | ゴム印風のスタンプ表現。白い紙に押すため、インクはタグ色を深めた濃色の派生色とし、薄い枠で囲う。傾きはカードごとに散らして手押しの不揃いさを出す（かすれのノイズマスクは描画負荷のため用いない） |
| 目印（NEW・お気に入り・メモ） | NEWピル（左上）／お気に入りの★シール（右上）／じぶんのメモのドット（右下）。いずれも白い紙の上で読みやすい配色とし、カード上では表示のみで操作は持たせない |
| 場面タグの色 | 代表7色：スピード対応 #F08A24（オレンジ）／資料品質 #3D85C8（ブルー）／調整力 #55B7BF（ティール）／気配り #F2A0BC（ピンク）／後輩サポート #33915F（グリーン）／アイデア #F5C63C（イエロー）／情報共有 #E8502F（バーミリオン）。カード上端の帯とタグピル・日付スタンプの派生色に用いる。**場面タグ自体は可変**であり、これらは代表的な7種への色割当にすぎない。新たに生成されたタグには規定のパレットから色を割り当てる |
| アバター | 全員 濃紺 #3A4A66 の1色に統一する。人ごとの色分けはしない（48px・イニシャルは白抜き・白リングを付ける） |
| 奥行き | カード上で奥行き（3D）を持たせるのはアバターのみ（translateZ 20px）。本文・タグ・日付はカードと同じ平面に置く |
| 拡大詳細の文字色 | アバターと同じ濃紺 #3A4A66 で統一する |
| ホバー | 控えめな動き。**ホバー中に限り、立体チルト（±6.5度）・浮き17px・淡い光沢（強さ.28）を出す**（2026-07のユーザー指示による。decision-log D-30）。静止時はまっすぐ置き、奥行きを持つのはアバターのみ。`prefers-reduced-motion: reduce` の環境では完全に停止する |
| カード→拡大詳細の遷移 | 表にカード・裏に詳細を貼った**1つの要素ごと裏返す**（380ms）。閉じるときは同じ動きを逆再生する（詳細設計 1.4.2） |
| モーション配慮 | `prefers-reduced-motion: reduce` の環境では遷移アニメーションを行わず、詳細を即時表示する |
| 押した波紋 | カードを押した位置から波紋を広げる。紙にインクがにじむ見立てで、色は場面タグ色。押した瞬間に実カードは隠れて複製が飛ぶため、複製の側で途中から続きを再生し、押した点から広がった輪がそのままカードに乗って裏返っていくようにする |

### 2.3.1 文字の大きさ（タイポグラフィ）

日本語は同じ px でも欧文よりずっと密になる。欧文の小文字が em の4〜5割しか使わないのに対し、日本語はほぼ全面を使うため、欧文向けの数値をそのまま持ってくると潰れて読めない（Material は公式に「CJK は欧文より font-size を +1px、line-height を +0.1em」と定めている）。

基準は**デジタル庁デザインシステム**に合わせる。

- 本文は **16 CSS px 以上**
- **14px** は付随情報や領域に制約がある場合に限る
- **14px 未満は原則として許容しない**
- 行送りは JLReq（日本語組版処理の要件）の「**1.7倍を既定、1.5〜2.0倍が望ましい**」に従う

なお **WCAG は px の最小値を規定していない**。SC 1.4.4 が求めるのは「200%まで拡大しても壊れないこと」であって「◯px以上」ではない。したがって上記は WCAG の要求ではなく、日本語UIとしての可読性基準として置く。

| トークン | 用途 | PC | スマホ（640px以下） |
|---|---|---|---|
| `--fs-note` | 凡例・単位・ごく短い語句。**これ未満は使わない** | 12px | 12.5px |
| `--fs-cap` | 補足・キャプション。付随情報の下限 | 13.5px | 14px |
| `--fs-ui` | ボタン・タブ・表など操作面の既定 | 14.5px | 15px |
| `--fs-body` | 読ませる文章。**ここを下回らない** | 16px | 16px |
| `--fs-lead` | 強めの本文・小見出し | 17.5px | 17.5px |
| `--fs-head` | 大きめのUI文字（短い一言のカード本文など） | 20px | 19px |
| `--fs-h2` | 節の題（`h2`）。**本文の1.25倍** | 20px | 20px |
| `--fs-h1` | 画面の題（`h1`）。**本文の1.5倍** | 24px | 20px |

見出しは本文との比で決める。**`h1`・`h2` は本文（16px）の1.25倍（＝20px）を下回らない**——下回ると、大きさで階層が読み取れない。スマホの `h1` が 20px なのは、390px 幅で画面の題と累計数を1行に置いており、21px 以上では折り返して主役のカードが下へ押し出されるためで、狭い画面では階層を太さで示す。

スマホとPCで推奨値そのものは大きく変わらない（本文はどちらも16px）。実際に効いてくる差は次の3点で、これを 640px 以下のメディアクエリで吸収する。

1. **入力欄はスマホで 16px 未満にしない**。iOS Safari は 16px 未満の `input` / `select` / `textarea` に焦点が当たると、ページごと勝手に拡大する（仕様どおりの挙動）。viewport の `maximum-scale` で止める手もあるが、利用者から拡大を奪うことになるため用いない
2. 画面が狭いぶん補助的な文字を詰めたくなるが、そこを縮めるといちばん先に読めなくなるため、逆に少し上げる
3. 見出しは画面幅なりに落としてよい

字間について：デジタル庁は `letter-spacing: 0`、Google Fonts も「CJK の本文にトラッキングは適用しない」としており、欧文とは方向が逆である。本サービスは感謝カードの本文に .06em を用いているが、これは「アルバムらしい空気感」を優先した意匠上の判断であり、可読性基準としては 0 が正である旨をここに明記しておく。

### 2.4 上司ダッシュボード（S06・S07）の設計方針

イシュー#27で新設・作り替えた上司ビューに固有の方針をまとめる（詳細な数値・実測は詳細設計 1.5 に譲る）。

| 方針 | 内容 |
|---|---|
| 順位表示は可、煽りは不可 | 上司向け画面では数値の多い順・少ない順の並び、大小の表現を用いてよい（2.基本方針・decision-log D-83・D-92）。ただし「最下位」等の煽る言い回しは用いず、静かに事実を並べる |
| じぶんのメモは集計にも使わない | 関係のネットワーク図・つながりの数・関係の変化のインサイトは、いずれもThanksCard由来の通数のみで組み立てる。**お気に入り・じぶんのメモを集計値・派生指標としても使わない**（原則8。メモの登録有無が漏れ出す形を避ける） |
| 配置は一度だけ計算して固定する | 関係のネットワーク図の力学的な配置は、開くたびに変わると「何かが変わった」と誤読されるため、初期化時に一度だけ計算して固定し、画面の幅・高さが変わったときだけ計算し直す（decision-log D-87） |
| ホバー限定にしない | 図的な要素の情報は、キーボード操作でも指の操作でも同じ内容に到達できるようにする。あわせて全メンバーぶんの内訳を常に文章でも出しておく（decision-log D-72・D-88） |
| カードは置かない | 個々のありがとうカードの一覧・拡大詳細は上司ビューに一切置かない。称賛材料は「1on1で使えるエピソード」として文章で持つ（decision-log D-85） |
| 数の出どころは1本 | メンバー間のやり取りの通数は、新たに独立した集計を作らず、既存の`shape.monthly`（本人向けカタチの推移と同じ数）から導く。数の出どころを二重に持たない（D-34の原則を踏襲。decision-log D-90） |

## 4. 外部連携設計

### 4.1 Slack

- Events API（message.channels 等）でパブリックチャンネルのメッセージを受信する
- 過去ログは conversations.history で初回取込バッチが最大1年分を取得する
- 取得スコープは導入企業の管理者が承認する

### 4.2 Microsoft Teams

- Graph API のチャネルメッセージ購読（change notifications）で受信する
- 過去ログは同APIの一覧取得で取り込む

## 5. 検出・分類設計（概要）

検出はルールベース前段とLLM判定の二段構成とする。前段で候補を絞ることでLLMコストを抑制する。
- 前段：bot・自動定型文の除外、感謝語彙辞書・感謝系絵文字による候補抽出
- LLM判定：対象発言と前後文脈を入力し、感謝該当性／宛先／場面タグ／皮肉判定／信頼度を得る。場面タグは固定分類ではなく、既存タグへの割当または新規タグの生成を行う
- 閾値制御：信頼度が基準以上のもののみカード化する。基準未満は保存しない
- 経緯抽出：感謝発言から同一スレッド・直前のやり取りを遡り、経緯と要約（オブリエのメモ）を生成する
- 学習：誤検出報告を判定プロンプトの追加事例および閾値調整に反映する

## 6. 通知設計

- 本人向け：週1回のメールダイジェストのみ。文言は「今週は、あたたかい言葉が3通とどいています」のような言葉調とする
- 上司向け：プッシュ通知は行わない。月次レポート生成時にアプリ内で知らせる
- 節目演出（F09）：通知は送らず、アプリ内でのみ控えめな帯として表示する。同時に出すのは1件、アルバムの高さは取らず、主要な情報（画面の題・累計数・説明文）も覆わない置き場に出す（詳細設計 1.8）。一度閉じたら同じ節目は再表示しない
- 禁止事項：順位・比較・催促（送りましょう等）を含む通知
- 文言：キザな言い回しを避ける。操作の結果は「保存しました」のように平易に伝え、「綴じました」等の比喩は用いない（「綴じる」はサービス名の由来・コンセプト説明にのみ使う）

## 8. 非機能設計（概要）

- 性能：一覧系APIは応答1秒以内を目標とし、カードはページング（30件単位）で取得する
- 性能（関係のネットワーク図）：配置の計算は画面幅・高さが変わったときだけ行い、常時は再計算しない（実測0.4ms。decision-log D-87）
- データ最小化：感謝と判定されなかったメッセージ本文は永続化しない
- 監査：閲覧・エクスポート・設定変更の操作ログを1年間保持する
